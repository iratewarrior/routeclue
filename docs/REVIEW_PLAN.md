## Оценка предложений

План A необходим, план B полезен после исправления ошибок ядра. Большой
рефакторинг в демон/XPC/Network Extension пока не оправдан: он расходится с
позиционированием explain/verify и увеличивает эксплуатационную сложность.
Профили и настройки GUI полезнее следующего декоративного редизайна.
Фоновое автоматическое применение маршрутов/DNS следует отложить до появления
проверяемого протокола применения, отката и тестирования смены сети.
Полноценное управление IPv6 требует отдельной разработки; наличие блокирующих
inet6-правил само по себе такой поддержкой не является.

Утверждения исходного аудита о PF и гарантированной совместимости со сторонними
firewall нельзя принимать без проверки. Изоляция anchor сама по себе не
доказывает его достижимость из активного ruleset и отсутствие утечек.
Отсутствие поддержки Swift 6 в прежнем режиме Swift 5 не является само по себе
доказательством гонок при выполнении. Оценки сроков аудита не подтверждены.

## Приоритет 0: достоверность и безопасность

1. Общий разбор BSD netstat для RouteManager и PathExplainer. В текущем
   RouteManager.status flags ошибочно берутся из row[3], интерфейс из row[5].
   На машине подтверждён заголовок `Destination Gateway Flags Netif Expire`.
   PathExplainer берёт последний элемент строки как интерфейс и теряет записи
   с Expire. Проверять короткие префиксы, host routes, scoped routes, ожидаемый
   шлюз и интерфейс. Убрать compactMap из строгого разбора адресов/CIDR.
2. PF: общий Enabled не равен защите TunnelGuard. Неизвестное состояние показывать
   явно. Ошибка запуска или ненулевой код pfctl validation не должны считаться
   успехом. Проверить достижимость anchor, глобальные опции внутри anchor,
   все конфигурационные интерполяции, IPv6 и владение enable-reference tokens
   (`pfctl -E`/`-X`, подтверждено локальной man page). Если безопасная активация
   невозможна без замены глобальных правил, отказывать с объяснением.
   Не сбрасывать чужие states/правила. Указать root bypass и существующие states.
3. Привилегированные пакеты: ошибка route add не должна маскироваться следующим
   `|| true`; ошибка копирования DNS — завершающим flush. Безопасные уникальные
   staging, валидация IP DNS-серверов и PF-входов. Батчинг не называть транзакцией
   без реализованного отката. Не перезаписывать повреждённый config defaults.
4. Verify/diff: Dictionary(uniqueKeysWithValues:) сейчас может упасть на дублях.
   Проверять policy-required subnets даже вне config; requiredZones должны
   проверять фактический scoped resolver, а не лишь ответ сервера.
5. Explain: сейчас blocked вычисляется по allowlist раньше проверки пути utun,
   что может объявить VPN-трафик заблокированным. Отделить предположение по
   конфигурации от фактического firewall. Source IP с интерфейса — оценка,
   не измерение исходящего соединения. IPv6 nameserver не обрезать split(:).last.

## Приоритет 1: полезные сценарии

1. Поле host/URL и явная кнопка Paste вместо автоматического чтения clipboard.
2. Debounce сетевых обновлений, исключение параллельных refresh, перечитывание
   config, сохранение причин ошибок Heal All.
3. Настройки подсетей и DNS в GUI: валидация, раздельные Save и Apply.
4. CLI profiles list/save/use/import/export: безопасные имена, проверка
   содержимого, атомарная запись, тестирование в temp directory. Переключение
   профиля меняет конфигурацию, применение к сети — отдельное действие.
5. Согласовать README, ARCHITECTURE, SECURITY, POSITIONING, CHANGELOG с кодом:
   Swift 6 minimum, зависимость ArgumentParser, реальные ограничения и roadmap.

## Критерии приёмки

- Регрессионные проверки с реалистичными fixtures netstat, ошибочными CIDR,
  отказом pfctl validation, дублями policy/snapshot, shell quoting, повреждённой
  конфигурацией, профилями в временном каталоге.
- `swift build -c release` и `swift run -c release TunnelGuardSelfTest`.
- CLI help, валидный JSON, ненулевые exit codes при ошибках.
- `./Scripts/build-app.sh release` и отдельная визуальная проверка GUI.
- Отчёт исполнителя `docs/IMPLEMENTATION_REVIEW.md` с реальными командами,
  результатами и непроверенными ограничениями; затем независимое review Codex.
- Не изменять действующую сеть, PF, /etc/resolver и пользовательский config
  во время автоматических проверок. Не делать push/merge без дальнейшего задания.
- Непроверенную защиту PF не объявлять принятой: root/network acceptance
  требует отдельной изолированной среды. Сборка и self-tests её не заменяют.
